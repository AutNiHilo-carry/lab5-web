# Lab5 生产订单与物流管理系统

无人机整机生产的**生产订单与物流管理系统**，围绕“工单 → 物料 → 工序 → 库存”这条主线，把计划、领料、派工、报工、入库与库存追溯串成一个闭环。

- **业务定位**：面向中小型整机装配场景的 MES 雏形，强调“单据驱动库存、过程可追溯”
- **系统规模**：24 张表、41 个外键、21 个唯一索引、4 个视图、3 个存储过程
- **工程形态**：零构建前端（Vue 3 + Element Plus）+ Express 接口 + MySQL 8 持久化

---

## 一、业务背景

无人机整机由机架、电机、桨叶、电调、飞控、电池、云台等零部件装配而成。生产管理的难点不在“记录”，而在三件事：

1. **物料齐不齐**——计划下达后，仓库到底缺什么、缺多少，必须一眼看清；
2. **工序走到哪**——六道工序之间的在制品如何流转，谁交给谁、交了多少；
3. **库存准不准**——领了多少、退了多少、入了多少，最终结存能不能对上账。

系统把这三件事拆成可校验的规则：物料需求由 BOM 算出，在制品由工序数量约束，库存由单据确认驱动。任何一步都不能“手工改数”，只能通过业务动作改变结果。

### 业务主线

```
建单 → 审核下达 → 领料 → 派工 → 报工 → 成品入库 → 库存与流水
      │            │        │        │          │
      ├ 生成物料需求 ├ 扣减库存 ├ 记录移交 ├ 校验待入库
      └ 生成工序任务 └ 回写已领 └ 约束下道 └ 达标自动完工
```

## 三、核心业务规则

规则是系统的“骨架”，每条都对应一个真实场景。

### 1. 下达即快照

审核下达时，系统按 `BOM 单件用量 × 计划数量` 生成物料需求，并按 BOM 指定的路线复制出工序任务。

**为什么这样做**：工单一旦下达，就代表“这一批按当时的配方和工艺生产”。此后修改 BOM 或路线，不能影响已经在制的订单，否则数量与工艺会对不上。

### 2. 单据驱动库存

库存只能由**已确认**的出入库单据改变：

- 草稿状态不动库存；
- 确认时在事务内逐行校验（库存是否足够、退料是否超领）；
- 全部通过才变动余额、写入流水，并回写工单的已领/已退/已入库数量；
- 任意一行失败，整单回滚，不会出现“扣了一半”的中间状态。

**为什么这样做**：库存是结果，不是输入。没有单据就没有变动，才能保证每一笔都有据可查。

### 3. 物料齐套才能报工

报工前系统会计算每项物料的“需求 − 已领”，只要还有未领足的物料就拒绝报工，并提示缺哪几项。

**为什么这样做**：车间没料就开不了工。校验放在报工（开工登记）这一刻，既不阻碍提前派工排产，又能挡住“无米之炊”。

退料不会让“已领料”的事实失效——退料是把多余的料退回，不是没领过。

### 4. 工序之间的数量约束

每道工序能报多少，取决于**上一道移交了多少合格品**：

```
本道可报 = 上道合格数 − 本道已处理（合格 + 报废）
首道可报 = 工单计划数
```

本道把上道移交的数量全部处理完，状态自动变为“已完成”。报废单独记录，不进入下道。

**为什么这样做**：报废是真实损失，如果报废品继续流转，后面的数量就会虚高。

### 5. 报工即移交

报工时可以指定“接收人”（默认带出下一道工序的负责人）。这条报工记录同时就是一次工序移交的凭证：交了多少、交给谁、什么时候交的，都能追到。

### 6. 入库与完工

- 成品入库数量不能超过“末道合格 − 已入库”；
- 末道工序的合格品全部入库后，工单自动判定为已完工；
- 完工不是人点出来的，是流程走完的结果。

### 7. 金额只记在两张单据上

采购入库与销售出库可以填一个**总金额**（选填、不含税）；生产领料、生产退料、成品入库不涉及金额。

**为什么这样做**：这一版的目标是“能算采购支出和销售收入”，不做库存成本核算。金额记在单据主表而不是明细行，避免拆行、改数量后还要重算单价。

## 四、系统设计

### 4.1 总体架构

```
┌──────────────────────────────┐
│ 浏览器（静态页面，无需构建）      │
│ Vue 3 + Element Plus          │
│  本地数据 / 内存数据 / 真库       │
│        └── 统一接口层 MES.api   │
└───────────────┬──────────────┘
                │ JSON + Bearer Token
┌───────────────▼──────────────┐
│ Express 服务                   │
│ 路由 → 业务服务 → 仓储          │
│  ├─ MySQL 仓储（持久化）        │
│  └─ 内存仓储（无库也能测）       │
└───────────────┬──────────────┘
                │ 连接池 / 事务
┌───────────────▼──────────────┐
│ MySQL 8（InnoDB）              │
│ 24 表 + 4 视图 + 3 存储过程     │
└──────────────────────────────┘
```

三层职责清晰：页面只负责展示与交互，接口层负责规则与事务，数据库负责约束与持久化。

### 4.2 数据模型

24 张表按业务域分为五组：

| 业务域 | 表 | 说明 |
| --- | --- | --- |
| 组织与权限 | `factory`、`workshop`、`department`、`role`、`sys_user` | 车间与部门平级挂工厂；角色以 JSON 保存页面权限 |
| 主数据 | `unit`、`item`、`partner`、`equipment`、`workstation`、`tooling` | 物料、单位、往来单位与生产资源 |
| 工艺 | `routing`、`routing_detail`、`bom`、`bom_detail` | 工序顺序与单件用量；BOM 指定路线 |
| 生产 | `work_order`、`order_material`、`order_task`、`work_report` | 工单、需求、任务与报工 |
| 仓储 | `warehouse`、`stock_doc`、`stock_doc_detail`、`stock_balance`、`stock_flow` | 单据、明细、余额与流水 |

**核心表设计**

| 表 | 关键字段 | 设计要点 |
| --- | --- | --- |
| `work_order` | `no`、`name`、`item_id`、`plan_qty`、`status` | 名称给现场看、编号用于追溯；同时记录负责工厂与主要车间 |
| `order_material` | `req_qty`、`picked_qty`、`returned_qty` | 下达时生成；欠料 = 需求 − 已领 + 已退 |
| `order_task` | `seq`、`equip_done_qty`、`scrap_qty`、`inbound_qty` | `seq` 表示顺序；上道合格数约束本道可报量 |
| `work_report` | `qual_qty`、`scrap_qty`、`receiver_id` | 一次报工 = 一次移交，接收人可追溯 |
| `stock_doc` | `doc_type`、`partner_id`、`amount`、`status` | 五种业务类型共用一套单据；金额只在这张表 |
| `stock_flow` | `change_qty`、`before_qty`、`after_qty`、`doc_id` | 每次变动留痕，结存 = 流水累加 |

### 4.3 关键设计取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 工艺路线与产品的关系 | 路线不绑定产品，由 BOM 指派 | 一条路线可被多个产品复用，换工艺只改 BOM 一处 |
| 工单与车间的关系 | 工单绑“主要车间”，执行车间由设备/工位体现 | 一张单可能跨车间生产，绑的是归口责任而非执行位置 |
| 库存的记账方式 | 只由单据累加，不设期初值 | 保证“结存 = 入库 − 出库”永远成立 |
| 报工与移交流程 | 报工即移交，不单独建转移单 | 数量约束已能表达流转，少一步操作，账更清楚 |
| 供应商与客户 | 合并为一张表，用类型区分 | 字段高度重合，减少一张表和一套页面 |
| 物料类别 | 成品/半成品/原材料固定三类，另加自由填写的细分类别 | 类别承担“能否投产”的判断，不能随意扩展；细分只做归类 |
| 角色权限 | 页面级（菜单 + 路由 + 接口三处一致） | 演示与教学场景够用，改造量可控 |
| 数据源 | 本地 / 内存 / MySQL 三套，共用同一套规则 | 没有数据库也能演示，接口层可脱离数据库测试 |

### 4.4 代码组织

```
lab5-web/
├─ index.html            页面入口
├─ app/                  前端：core → db → api → session → ui → layout → views → app
├─ server/               后端：routes → services → repositories（mysql / memory）
├─ db/                   建表、演示数据、存储过程、视图与核对查询
├─ scripts/              自检与联调脚本
└─ vendor/               Vue / Vue Router / Element Plus 本地化文件
```

前端按依赖顺序拆成十来个脚本文件，后端按“路由 / 服务 / 仓储”分层，两侧都不依赖构建工具或框架脚手架。

| 角色 | 职责 | 默认可见 |
| --- | --- | --- |
| 系统管理员 | 系统配置、角色权限、全部业务 | 全部页面 |
| 计划员 | 建单、审核下达、派工、编制领料与入库单 | 总览、基础资料（部分）、工艺、生产、库存单据与余额 |
| 操作员 | 接收派工、按工序报工 | 总览、生产工单、工单进度、工序任务、报工记录 |

权限在三个层面同时生效：

1. **菜单**：没有权限的菜单不显示；
2. **路由**：手工输入地址会被拦截并跳回可用页面；
3. **接口**：后端按模块校验，返回 403，避免绕过页面直接调接口。

管理员可在“角色权限”页面逐项勾选，保存后对应角色重新登录即可生效。

系统内置几个演示账号（密码统一为 `123456`，仅作演示）：`admin` 张明（管理员）、`planner` 李彦（计划员）、`op_assembly` 王强（操作员）、`warehouse` 陈静（仓管员）。

## 六、关键页面说明

- **生产总览**：四张指标卡（在制工单、累计合格产出、待办、库存预警）+ 近 7 天产出柱状图 + 工序在制分布 + 待办与最近报工。
- **工单进度**：每张在制工单一条工序步骤带，圆点颜色表示完成/进行/等待前置，连接线随完成情况点亮，超过一页自动分页。
- **工序任务**：派工与报工的统一入口，状态列会区分“待开始”和“等待前置”（上道还没移交合格品）。
- **生产进度**：按工单看每道工序的在制品与待入库数量，用来回答“现在做到哪、还差多少”。
- **库存单据**：新建时按业务类型动态显示供应商、客户或关联工单；确认时整单校验；列表展示往来单位与金额。
- **出入库流水**：可按仓库、业务类型、单据号或物料筛选，每一行都能追到来源单据。

## 九、已知限制与后续规划

- 口令以明文保存、令牌存放于服务内存，正式环境应改为哈希 + JWT；
- 列表未做服务端分页，报工记录与流水按最近若干条展示；
- 缺少并发场景下的乐观锁；
- 权限到页面与接口级，未细化到按钮；
- 成本核算只做到单据金额，库存金额（移动加权平均）尚未实现；
- 未做多租户与操作审计日志。

后续可从安全加固、分页与索引优化、按钮级权限、库存成本四个方向继续完善。
